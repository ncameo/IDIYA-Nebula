# Customer Management

Generated by Nebula from spec/spec.json v1.1. Do not edit by hand; change the spec.

Owns the Customer entity (E-02) for the agent's conversational list, show and de-activate, and the
Status state machine SM-01 transition T-01 (Active → Inactive). Spec v1.1 defines no workflows and
no checks; the De-activate guard comes from action A-09 and SM-01.

Out of scope: re-activating a customer (T-02, AS-26); creating or editing customer details (no
tool, AS-30); deactivation reason options (AS-25); Apply promo and promo codes (AS-27);
Subscription, Invoice and Payment method data (OOS-05); deleting customers; Products (the
`product-management` skill). The S-03/S-04 forms call the same tools through EP-005..EP-007
themselves; their behaviour is not driven by this skill.

## State transitions

| From | To | Trigger | Tool | Guard |
|---|---|---|---|---|
| Active | Inactive | Admin confirms De-activate | `np_update_customer` (changes.Status=Inactive) | Customer.Status is Active, read by `np_get_customer` in the same run |

Illegal — do not attempt, report instead:

- Inactive → Inactive: "Customer is already inactive."
- Active → Active: "Customer is already active."
- Inactive → Active (T-02): out of scope v1.1, no tool; say that re-activating a customer is not
  available in this version.

## Flow

Pick the intent the admin asked for, then follow its steps only.

1. **List customers** — call `np_list_customer` (no parameters). If the admin named a Name, narrow
   the returned list to records whose Name matches; if the admin asked for active customers only,
   narrow it to Status Active (AS-24). Present Name and Status per customer.
2. **Show one customer** — identify the CustomerId: if the admin named the customer, call
   `np_list_customer` and select the matching record; if several match, ask which one. Then call
   `np_get_customer` with `CustomerId`. If `found` is false, say the customer was not found and
   stop. Present Name, Status, CustomerSince, ContactName, Email, Phone and StripeCustomerId.
3. **De-activate a customer** — resolve the CustomerId as in step 2 and call `np_get_customer`.
   - If `found` is false, say the customer was not found and stop.
   - If Status is Inactive, stop and say "Customer is already inactive."
   - If Status is Active: ask the admin for the deactivation reason and an optional internal note,
     both as free text (no reason list exists in v1.1; never offer options of your own). Restate
     the change, get confirmation, then call `np_update_customer` with `CustomerId` and
     `changes` = { Status: Inactive, DeactivationReason, DeactivationNote } (omit the ones not
     given). Report the result in plain language.
4. **Activate / re-activate** — if the customer is Active, say "Customer is already active.";
   if Inactive, say re-activation is not available in this version. Never call
   `np_update_customer` for this.
5. Reply to the admin as defined in the agent instruction's Output section.

A refusal or error message names the field and the problem; never repeat the record's values in
logs or run notes.

## Failure handling

| Tool | Primary | Fallback | On total failure |
|---|---|---|---|
| `np_get_customer` | SQL MCP Server `read_records` | retry once after 2s | stop: no Customer data changed, tell the admin the data could not be read, log error |
| `np_list_customer` | SQL MCP Server `read_records` | retry once after 2s | stop: no Customer data changed, tell the admin the data could not be read, log error |
| `np_update_customer` | SQL MCP Server `update_record` | retry once after 2s | stop: leave the Customer status unchanged, tell the admin the request could not be completed, log error |

No database guard, trigger or stored procedure exists for Customer in spec v1.1 (database layer
not generated); the Status check in step 3 is the only guard, so never skip it. A schema rejection
from the server is reported to the admin as a field problem, without values.
