# Product Management

Generated by Nebula from spec/spec.json v1.0. Do not edit by hand; change the spec.

Owns the Product entity (E-01) for the agent's conversational CRUD. Product has no state machine
(Visibility is a label, AS-02), and spec v1.0 defines no workflows and no checks.

Out of scope: deleting products; Subscription, Customer, Inquiry, Marketing Leads and any other
entity; live Stripe price lookup (OOS-04). The S-01/S-02 forms call the same tools through
EP-001..EP-004 themselves; their behaviour is not driven by this skill.

## Entities and routing

| Entity | Layer | Read via | Write via | Notes |
|---|---|---|---|---|
| Product (E-01) | Slow | `np_list_product`, `np_get_product` | `np_create_product`, `np_update_product` | Shared catalog that changes on business events; read fresh for each request, never reuse records from an earlier run. |

## Flow

Pick the intent the admin asked for, then follow its steps only.

1. **List products** — call `np_list_product` (no parameters). If the admin named a Name, Category
   or Visibility, narrow the returned list to matching records before presenting it. Present Name,
   Category, Visibility and BillingType per product.
2. **Show one product** — identify the ProductId: if the admin named the product, call
   `np_list_product` and select the matching record; if several match, ask which one. Then call
   `np_get_product` with `ProductId`. If `found` is false, say the product was not found and stop.
3. **Create a product** — collect the required fields Name, Category, NoOfAppsAllowed, Visibility
   and BillingType, plus any optional fields the admin gives. Category must be PaaS or Managed;
   Visibility Public, Private or Draft; BillingType One time or Recurring. Never supply ProductId.
   Restate the values to the admin, get confirmation, then call `np_create_product`. Report the
   result in plain language.
4. **Update a product** — resolve the ProductId as in step 2 and call `np_get_product` to confirm it
   exists. Collect only the fields to change, restate the change, get confirmation, then call
   `np_update_product` with `ProductId` and `changes`. Never change ProductId.
5. Reply to the admin as defined in the agent instruction's Output section.

A refusal or error message names the field and the problem; never repeat the record's values in
logs or run notes.

## Failure handling

| Tool | Primary | Fallback | On total failure |
|---|---|---|---|
| `np_create_product` | SQL MCP Server `create_record` | retry once after 2s | stop: leave the Product unchanged, tell the admin the request could not be completed, log error |
| `np_get_product` | SQL MCP Server `read_records` | retry once after 2s | stop: no Product data changed, tell the admin the data could not be read, log error |
| `np_list_product` | SQL MCP Server `read_records` | retry once after 2s | stop: no Product data changed, tell the admin the data could not be read, log error |
| `np_update_product` | SQL MCP Server `update_record` | retry once after 2s | stop: leave the Product unchanged, tell the admin the request could not be completed, log error |

No database guard or stored procedure exists for Product in spec v1.0; a schema rejection from the
server is reported to the admin as a field problem, without values.
